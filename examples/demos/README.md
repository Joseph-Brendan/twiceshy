# Twiceshy demos

Six runnable demos, one per story from the launch guide. Each demo is a plain
`node` process. Demos 1 to 5 print a clear `PASS` or `FAIL` line and exit
non-zero on `FAIL`. Demo 6 only prints timings.

## Setup

You need **Node 22 or newer** (`node --version`).

```bash
npm init -y
npm install twiceshy better-sqlite3
npm install @twiceshy/mcp-proxy
npm pkg set type=module
```

The `twiceshy` command used by Demos 2, 4, and 5 comes from
`@twiceshy/mcp-proxy`, not from the `twiceshy` library. If it is not installed,
run the same commands as `npx -y @twiceshy/mcp-proxy <command>`.

In this repository, the demos are a workspace package, so
`pnpm install && pnpm build` at the root is enough, then run each demo:

```bash
pnpm --filter @twiceshy/example-demos demo1
```

## Demo 1: retries without and with Twiceshy

`demo1.js` sends the same refund three times with a rephrased `reason` each
time: three refunds without Twiceshy, one refund with it, because `keyFields`
makes the reason irrelevant to the action's identity.

Expected: `PASS Demo 1: a rephrased retry is the same refund`.

## Demo 2: the silent success (the Kola case)

`demo2.js` runs the slow-refund story twice against `demo.db`:

- Phase 1 sends one refund, lets the first attempt time out, sees attempts 2
  and 3 blocked with `IN_DOUBT`, then waits for the slow reply and shows the
  record upgraded to `SUCCEEDED`.
- Phase 2 does the same for a second transaction but closes the guard before
  the slow reply arrives, so the record stays `IN_DOUBT`. A person must settle
  it.

The script prints the exact `npx -y @twiceshy/mcp-proxy resolve ...` command
for the in-doubt record. To run the CLI yourself, use `twiceshy.config.json` in
this folder:

```bash
npx -y @twiceshy/mcp-proxy list --config twiceshy.config.json
npx -y @twiceshy/mcp-proxy show <id> --config twiceshy.config.json
npx -y @twiceshy/mcp-proxy resolve <id> --succeeded --by "<your name>" --config twiceshy.config.json
```

Expected: `PASS Demo 2: in doubt stops the retry, and the late reply upgrades it`.

## Demo 3: twenty calls at the same moment

`demo3.js` fires 20 identical bookings at once. Atomic claiming lets exactly
one run; the other 19 wait and receive its result.

Expected: `PASS Demo 3: twenty parallel calls make one booking`.

## Demo 4: put the proxy in front of an MCP server

`demo4.js` writes `proxy.config.json` with absolute paths built from this
folder, runs `doctor`, then starts the proxy over stdio and calls
`create_charge` three times and `get_count` once. The local counter server is
`counter-server.mjs`; nothing in it changes.

Expected: `PASS Demo 4: the proxy guards an unchanged MCP server`, with the
first charge returning `charged 1` and the next two starting with
`Twiceshy: this action already ran`.

If a failure happens before the MCP handshake, the client only sees
`Connection closed`; run the `doctor` step in the output above to see the real
reason.

## Demo 5: run doctor against a real server

`demo5.js` adds the official filesystem server to `proxy.config.json` and runs
`doctor` again. The first run downloads that server with `npx`, which can take
half a minute, so the demo downloads it once itself before `doctor` starts;
otherwise the proxy's 15-second connect timeout can expire while `npx` is still
fetching (Windows is especially slow at this). Read the GUARDED/open reasons
doctor prints, especially
`write_file` and `create_directory` (open because they claim to be idempotent)
against `edit_file` and `move_file` (guarded because they are destructive).

Expected: `PASS Demo 5: doctor explains a real server it has never seen`.

## Demo 6: measure the cost

`demo6.js` measures 1,000 guarded calls on `MemoryStore` and `SqliteStore` and
prints the milliseconds per call. It has no PASS or FAIL line: compare the
numbers with the hundreds of milliseconds a real payment API call takes.

## Files

| File | What it is |
|---|---|
| `demo1.js` to `demo6.js` | One script per demo. |
| `counter-server.mjs` | The local MCP server used by Demos 4 and 5. |
| `lib.mjs` | Shared helpers: PASS/FAIL, CLI runner, config writer, stdio client. |
| `twiceshy.config.json` | CLI config pointing at `demo.db`, the database Demo 2 creates. |
| `proxy.config.json` | Generated by Demo 4 with absolute paths; Demo 5 adds the filesystem server. |

Demo files create and delete their own databases, counter files, and
`proxy.config.json` as they run. Nothing else on your machine is touched.
